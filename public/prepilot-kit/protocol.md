# 해보기 3명 예비테스트 진행 대본

상태: 실행 준비. 사용자가 참여 가능한 학생 약 3명을 확보했다고 알려주었지만 실제 관찰·응답·후속 확인은 아직 진행하지 않았습니다. 최신 통합본의 main 배포와 진행자 QA 점검 후 사용합니다. 아래 시간은 예상이며 성과값은 없습니다.

## 이번에 알아볼 것

설명 없이 첫 수정·실행·회고·비교에 도달하는지, 다음에 할 작은 일과 이유를 자기 말로 설명할 수 있는지 확인합니다. 학생을 평가하는 시험이 아닙니다. 세 사람은 제품의 큰 막힘을 찾는 작은 편의 표본이며 직무별 선호·적성·학과 전체의 효과를 비교할 표본이 아닙니다.

| 참여 번호 | 첫 직무       | 둘째 직무      |
| --------- | ------------- | -------------- |
| S01       | 프론트엔드    | 백엔드         |
| S02       | 데이터 분석   | AI 엔지니어    |
| S03       | 보안 엔지니어 | 클라우드 / SRE |

각자 두 코드 직무, 여섯 직무가 한 번씩 배치됩니다. 직무별 한 번의 관찰로 난이도 차이를 단정하거나 순서 효과를 분리할 수 없습니다. 정식 12명 파일럿은 P01~P12이며 별도로 진행합니다. 예비테스트를 한 학생이 나중에 정식 파일럿에도 참여하면 이미 사용한 경험을 기록하고 새 사용자 결과로 합치지 않습니다.

## 진행자가 먼저 준비할 것

1. main의 현재 배포 버전·날짜·브라우저를 적습니다. QA 번호로 시작→수정→실행→회고 저장→비교와 참여 철회가 정상인지 확인합니다. 저장 충돌 등 큰 장애가 있으면 학생 진행 전에 해결합니다.
2. 세 학생에게 S01/S02/S03을 각각 배정합니다. 실명·학번은 양식에 적지 않습니다. 연락처와 연락 동의 원본은 접근 제한 공간에 따로 보관합니다. 안내 메시지는 `invitation.md`를 직접 전달하며 이 도구가 연락을 발송하지 않습니다.
3. 기존 기록이 없는 개인 브라우저 프로필을 권장합니다. 기존 기록을 임의로 삭제하지 않습니다. 팀원 화면을 같은 브라우저 계정으로 공유하지 않습니다. 코드 체험은 키보드가 있는 데스크톱을 권장합니다.
4. 작성용 파일은 공개 저장소 밖의 접근 제한 폴더로 복사합니다. `participants.csv` 3행, `observations.csv` 6행, `followup.csv` 3행과 문제 정리용 `findings.csv`는 모두 빈 응답 양식입니다.

## 시작 대본 — 약 3분

“해보기를 이용하면서 어디가 자연스럽고 어디가 막히는지 보려고 해요. 코딩 실력이나 적성을 평가하지 않고 참여 여부가 성적에 영향을 주지 않아요. 언제든 쉬거나 그만둘 수 있어요. 이름·학번·연락처·비밀키는 코드나 회고에 적지 말아주세요.”

관찰에 동의하는지 확인합니다. 활동 분석 수집과 7일 뒤 연락은 각각 별도로 선택하게 합니다. 앱 분석 수집에 동의하지 않아도 체험과 관찰은 가능합니다. 녹화는 기본으로 하지 않습니다. 별도 녹화 동의 없이 녹화하지 않습니다.

활동 수집을 선택한다면 도움말의 ‘체험 개선 참여’에서 **S번호를 먼저 고른 뒤** 켭니다. 이미 잘못 켰다면 끄고 분석 삭제 성공을 확인한 뒤 올바른 번호로 다시 켭니다. 이전 기간은 삭제되므로 번호 변경 시점을 관찰에 표시합니다. QA·P번호로 학생 예비테스트를 기록하지 않습니다.

첫 체험 전에 JavaScript 경험(없음/기초/프로젝트), AI 코딩 도구 사용(없음/가끔/자주/미응답), 아래 명확성 질문을 받습니다. 사전 답을 받기 전에 체험의 기대 효과나 정답을 설명하지 않습니다.

“최근 직무를 알아볼 때 어떤 방식으로 알아봤나요?”도 중립적으로 묻습니다. 글·영상·수업·프로젝트·기타·미응답으로 분류하되 불편했다고 전제하지 않습니다. 사전 답변은 다음 과제 정답이나 예상 효과를 알려주는 데 사용하지 않습니다.

## 사전·사후에 그대로 읽는 질문

“다음에 무엇을 배울지 얼마나 분명한가요?”

1 전혀 분명하지 않다 / 2 별로 분명하지 않다 / 3 보통이다 / 4 어느 정도 분명하다 / 5 매우 분명하다.

사전은 첫 체험 이전, 사후는 비교 이후 또는 중단 직후에 받습니다. 무응답은 빈칸이고 0점·1점으로 바꾸지 않습니다. 사후 답으로 사전을 채우지 않습니다.

## 체험 대본 — 두 직무 각 약 10분

“첫 번째로 [배정된 직무]의 작은 업무를 해보세요. 필요하면 화면의 문법 예제·힌트·참고 풀이를 이용해도 돼요.”

처음부터 버튼 위치나 고칠 코드를 알려주지 않습니다. 첫 행동, 수정까지 시간, 실행까지 시간, 도움 사용, 회고 제출, 서버 저장 확인을 구분해 관찰합니다. 모든 테스트를 통과하지 않아도 직접 수정·실행하면 회고할 수 있다는 기존 원칙을 유지합니다.

3분 이상 막히면 “지금 화면에서 다음으로 무엇을 할 수 있을까요?”라고 중립적으로 묻습니다. 개입은 0 없음 / 1 중립 질문 / 2 위치 안내 / 3 풀이 안내로 표시합니다. 10분 정도가 지나도 부담스럽다면 중단·휴식을 제안합니다. 시간은 강제 제한이나 성적 기준이 아닙니다. 정답 안내 후 완료했다면 자력 완료라고 쓰지 않습니다.

첫 회고를 남기면 “같은 방식으로 두 번째 [배정된 직무]를 해보세요”라고 안내합니다. 기록 저장 실패·미저장 초안이 보이면 화면의 재시도·복구 안내를 따르고 관찰 문제로 기록합니다. 학생의 원문 코드·질문·회고는 관찰 양식에 복사하지 않습니다.

## 비교·인터뷰 대본 — 약 7~12분

“두 작업의 회고를 비교해보세요. 더 해보고 싶은 일과 다음에 할 작은 일 하나를 알려주세요.”

1. 같은 사후 명확성 질문을 받습니다. 중단한 학생도 가능한 범위에서 답하게 합니다.
2. “어떤 부분이 재미있거나 어려웠나요?” 원문을 길게 복사하지 말고 화면/문법/설명/저장/시간 등 분류와 비식별 요약을 남깁니다.
3. “이 직무에서 직접 바꾼 것은 무엇인가요?” 자기 말로 설명했는지 여부를 기록합니다. 맞고 틀림의 실력 점수를 만들지 않습니다.
4. “다음에 할 작은 일은 무엇이고 왜 골랐나요?” 제안이 노출됐다는 사실, 실제 선택, 이유를 설명한 사실을 구분합니다.
5. “혼자였다면 어디에서 그만뒀을 것 같나요?” 문제 화면과 영향(진행 불가/큰 혼란/작은 불편)을 기록합니다.
6. 원하면 마지막에 게임 하나를 체험합니다. 게임은 코드 직무 완료 수에 섞지 않습니다.

기존 PRD의 문제를 확인하는 추가 질문:

- “직접 해본 뒤 이 직무에서 하는 일을 다르게 이해한 부분이 있나요? 바뀌지 않았어도 괜찮아요.” 이해 변화 있음/없음/미응답과 실제로 업무를 자기 말로 설명했는지를 구분합니다. 긍정 응답을 유도하지 않습니다.
- “도움이 필요했던 순간에 무엇을 해봤나요? 그 뒤 직접 바꿀 부분을 찾을 수 있었나요?” 도움 이용 사실과 다음 수정 파악 여부를 구분하며 도움이 필요 없었다면 해당 없음입니다.
- 다음 활동 하나와 이유를 자기 말로 설명하는 질문, 사전·사후 동일 명확성 질문은 그대로 유지합니다. 재미 점수만으로 직무 이해·막힘 해결·학습 방향 문제가 해소됐다고 결론내리지 않습니다.

심사 기준(기술 30·창의 25·실용 25·발표/협업 20)에 맞춰 발표할 때도 기능 구현·기술 검사는 별도 근거로, 학생 응답은 실용성 탐색 근거로 구분합니다. 평가 배점을 학생의 점수나 서비스 효과 점수로 환산하지 않습니다.

전체 약 30~40분은 안내용 예상입니다. 실제 시간을 기록하며 학생의 중단·거절·쉬기 요청을 우선합니다.

## 7일 뒤 — 후속 연락 동의자, 미완료자 포함

“지난번 고른 활동을 실제로 시작했나요? 예 / 아니오 / 기억나지 않음. 시작했다면 어떤 일을 언제 했나요?”라고 직접 확인합니다. 미시작 이유는 시간/난이도/방향 미정/다른 우선순위/기타로 분류합니다. 연락하지 않음과 연락했지만 무응답을 구분합니다. 무응답은 미시작이 아닙니다. 자기 응답을 객관적 실행 증거라고 쓰지 않습니다. 자발적으로 보여준 근거는 확인 여부만 표시하고 원본은 복사하지 않습니다.

## 결과 정리 — 세 사람의 빈칸을 실제 값으로 채운 뒤

- 시작·완료·중단·분석 동의·후속 연락 동의 인원을 각각 n/3으로 제시합니다. 결과가 없는 현재는 미실시입니다. 60%·40%·70% 목표 달성이나 정확도를 주장하지 않습니다.
- 사전/사후 유효 쌍 수와 각 변화값을 함께 봅니다. 작은 표본의 평균만으로 제품 효과를 단정하지 않습니다. 유효 쌍이 없으면 변화율을 계산하지 않습니다.
- 첫 수정/실행까지 시간은 도움을 받았는지와 함께 보고합니다. 누락 이벤트를 실제 포기·미저장으로 단정하지 않고 관찰 양식과 대조합니다.
- 막힘을 `findings.csv`에 비식별 요약으로 적고 관련 인원/유효 관찰 인원을 함께 표시합니다. 진행 불가·저장/삭제 오류부터 재현하고 수정 이슈와 연결합니다. 세 사람 의견을 일반화하거나 적성 순위로 만들지 않습니다.
- 공개 발표에는 비식별 집계·허락한 짧은 요약만 쓰고 학생 원문·연락처·응답 파일을 저장소에 올리지 않습니다. 접근 제한 응답 파일과 연락처는 종료·7일 확인 이후 30일 안에 폐기합니다. 앱 이벤트는 기존 30일 보관과 철회 정책을 따릅니다.

## 이벤트 집계

```sh
node scripts/report-analytics.mjs --since YYYY-MM-DD --until YYYY-MM-DD --cohort prepilot > /private/path/prepilot-events.json
```

날짜는 UTC이고 `until`은 제외 경계입니다. S01~S03만 집계합니다. 기본 `all`은 일반 이용+정식 P번호이며 S번호는 제외 수(`quality.prepilotExcluded`)로 표시합니다. `pilot`도 S번호를 제외합니다. QA는 기본 제외하며 예비테스트 분모에도 넣지 않습니다. 출력은 원본 소유자·동의 토큰·세션/여정 ID 없는 집계입니다. 실제 학생 수·명확성·선택 이유 설명·7일 시작은 진행자 양식에서 별도로 확인합니다.
